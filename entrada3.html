Scripts de shell que no deberías escribir (pero escribirás)

Un homenaje a los one-liners que funcionan una sola vez, en una sola máquina y bajo una sola fase lunar.

2026-11-089 min de lecturapor 0xBLOG
/inicio/archivo/contacto
[advertencia] Los ejemplos son didácticos. Pruébalos con datos temporales y entiende cada comando antes de ejecutarlo.

El shell permite resolver tareas en segundos. También permite borrar en segundos algo que llevaba años guardado. La diferencia entre una automatización útil y un accidente suele ser una validación, una comilla o una ruta escrita correctamente.

El clásico: variables sin comillas

Si una ruta contiene espacios, una variable sin comillas puede convertirse en varios argumentos. Cita las expansiones cuando representen rutas o valores que deban tratarse como una sola pieza.

archivo="mi carpeta/notas.txt"
cat "$archivo"

Las comillas no arreglan todos los problemas, pero evitan muchas divisiones y expansiones inesperadas.

Usar rm -rf sin comprobar la ruta

Los comandos destructivos merecen una pausa. Antes de eliminar algo desde un script, valida que la variable tenga valor y que la ruta esté dentro del directorio esperado. Para pruebas, imprime primero lo que el script haría.

printf 'Se procesaría: %s\n' "$directorio"

Ignorar los errores

Un script que sigue adelante después de una operación fallida puede producir resultados engañosos. En Bash, set -euo pipefail puede ayudar a detectar algunos errores, pero no sustituye la revisión: su comportamiento tiene excepciones y hay que entenderlo.

#!/usr/bin/env bash
set -euo pipefail

Parsear texto con for

Usar for archivo in $(comando) no es una forma segura de recorrer nombres que contienen espacios o caracteres especiales. Para archivos, es mejor apoyarse en mecanismos que preserven los nombres correctamente.

find ./datos -type f -print0 |
  while IFS= read -r -d '' archivo; do
    printf 'Archivo: %s\n' "$archivo"
  done

Escribir un one-liner imposible de leer

Un comando compacto puede ser divertido, pero si otra persona no puede entenderlo, será difícil mantenerlo. Usa nombres claros, separa etapas y comenta las decisiones no obvias.

No probar antes de automatizar

Antes de ejecutar un script sobre información real:

  • Prueba con una copia de los datos.
  • Incluye una opción de simulación cuando el script haga cambios.
  • Registra los errores y el resultado de cada etapa importante.
  • Verifica rutas, permisos y dependencias.

La regla que me salva más tiempo

Si un comando modifica o elimina archivos, primero haz que explique qué va a modificar. Cuando puedas revisar esa lista y te parezca correcta, recién entonces habilita la operación real.

Los scripts no necesitan ser ingeniosos: necesitan ser predecibles. El mejor atajo es el que entiendes cuando vuelves a leerlo meses después.
